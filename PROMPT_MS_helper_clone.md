# Промпт: создание приложения MS_helper (сортировщик медиаархива)

> Этот документ — готовое задание-спецификация. Его можно передать разработчику
> или ИИ-ассистенту целиком, чтобы получить работающее приложение, аналогичное
> **MS_helper** (`media-sorter`).

---

## 1. Роль и задача

Ты — senior Python-разработчик. Спроектируй и реализуй **портативное настольное
приложение для наведения порядка в домашнем фото- и видеоархиве** под Windows.

Приложение должно решать три независимые задачи:

1. **Сортировка «свалки»** — берёт папку с беспорядочными файлами и раскладывает
   их по структуре `Год/Месяц/тип`, переименовывая по дате съёмки.
2. **Поиск и изоляция дубликатов** — файлы с совпадающим содержимым (MD5)
   отправляются в отдельную папку, не удаляясь.
3. **Реорганизация уже существующего архива** — приведение старых папок
   (`2017`, `Фото 2018`, `05.2024 Ч`) к единой схеме именования.

Дополнительно: выделение «мусора» (мелкие фото и короткие видео) в отдельную
папку и ведение подробных отчётов.

**Ключевой принцип: ничего не удалять.** Любая операция — только перемещение
файла в другую папку. Удаление файлов приложением не предусмотрено вообще.

---

## 2. Пользовательские сценарии

- Пользователь копирует фото с телефонов, карт памяти, из мессенджеров в одну
  папку `Unsorted`. Запускает приложение → получает разложенный архив.
- Пользователь хочет сначала увидеть план, ничего не трогая → `--dry-run`.
- Пользователь повторно прогоняет сортировку после добавления новых файлов →
  существующие не перезаписываются, новые получают суффиксы `_1`, `_2`.
- Пользователь хочет привести в порядок архив, собиравшийся 15 лет вручную →
  запускает второй скрипт реорганизации на корне архива.

## 3. Технологический стек и ограничения

- **Python 3.10+**, только стандартная библиотека там, где это возможно.
- Внешние зависимости (минимум):
  - `Pillow` — чтение EXIF из JPEG/PNG/TIFF/HEIC;
  - `pillow-heif` — поддержка HEIC/HEIF (опционально, регистрируется при старте);
  - `ExifRead` — чтение EXIF из RAW (CR2, CR3, NEF, ARW, DNG, RAW).
- **`ffprobe`** (из пакета ffmpeg) вызывается как внешний процесс для метаданных
  и длительности видео. Если его нет в системе — программа обязана работать
  дальше, а не падать: переходить к следующему источнику даты.
- **GUI — только `tkinter`/`ttk`** (не требует установки).
- Приложение должно работать **без установки**, из любой папки
  (portable-режим).
- Опциональные зависимости не должны ломать импорт модуля при их отсутствии —
  оборачивай в `try/except ImportError` и пиши в лог `debug`.

## 5. Подсистема 1: сортировка

### 5.1. Определение даты съёмки (`date_extractor.py`)

Функция `get_creation_date(path) -> tuple[datetime | None, str | None, bool]`
возвращает `(дата, источник, is_approximate)`.

**Приоритет источников:**

| # | Источник | Как | `is_approximate` |
|---|---|---|---|
| 1 | EXIF фото | `DateTimeOriginal` → `DateTimeSubSecOriginal` → `DateTimeDigitized` → `DateTime` | `False` |
| 1 | RAW EXIF | `exifread`, те же теги в `EXIF DateTimeOriginal` | `False` |
| 2 | Видео | `ffprobe`: `format.tags.creation_time` → `stream.tags.creation_time` → `stream.tags.date` | `False` |
| 3 | Имя файла | регулярные выражения (см. ниже) | `False` |
| 4 | `mtime` | `path.stat().st_mtime` | **`True`** |

Важно: `mtime` — **последний** фолбэк, чтобы файл никогда не оставался «без
даты» и всегда попадал в структуру года/месяца. Файл помечается как
`is_approximate=True`, и это видно в отчёте.

**Учёт часового пояса:** если в EXIF есть `OffsetTimeOriginal`/`OffsetTime`,
применить смещение к дате (`_apply_offset`), иначе дата останется «плавающей».

**GPS-восстановление даты (опционально, но описано в оригинале):** собрать
индекс `(round(lat,3), round(lon,3)) -> datetime` по уже обработанным файлам.
Если у файла нет даты, но есть GPS — найти соседей в радиусе ~0.001°
(~100 м) и взять их дату как приблизительную.

**Шаблоны дат в имени файла** (порядок важен — от специфичного к общему):

1. `IMG_20240513_142035.jpg`, `VID_20240513_142035.mp4`,
   `Screenshot_20240513-142035.png`, `20240513_142035.mp4`
2. `2024-05-13 14.20.35.jpg`, `2024-05-13_14-20-35.jpg`,
   `Screen Shot 2024-05-13 at 14.20.35.png`, `photo_2024-05-13_14-20-35.jpg`
3. `IMG-20240513-WA0001.jpg` (WhatsApp), `PXL_20240513_123456.jpg`,
   `VID-20240513-WA0001.mp4`
4. `2024-05-13.jpg`, `2024_05_13.jpg` (только дата)
5. `20240513.jpg` (только дата, слитно)
6. `PXL_20240513_123456` — дата + время (Pixel/Samsung)

Дата из имени всегда валидируется (`datetime(...)` в `try/except ValueError`),
невалидные комбинации (`2024-13-45`) отбрасываются.

**Кэширование:** чтение EXIF обернуть в `@lru_cache(maxsize=4096)` по строковому
пути — файл не читается дважды (сначала дата, потом GPS).

### 5.2. Множества расширений

```python
IMAGE = {.jpg .jpeg .png .heic .heif .tiff .tif .raw .cr2 .cr3 .nef .arw .dng}
RAW   = {.raw .cr2 .cr3 .nef .arw .dng}          # подмножество IMAGE
VIDEO = {.mp4 .mov .avi .mkv .mts .3gp}
SUPPORTED = IMAGE | VIDEO
```

Множества должны быть `frozenset` и **не пересекаться** между IMAGE(без RAW) и
VIDEO — на это пишется тест.

### 5.3. Дубликаты (`hash_utils.py`)

```python
get_file_hash(path, buffer_size=8192) -> str   # MD5, чтение порциями
build_hash_index(files) -> dict[str, list[Path]]
find_duplicates(index) -> dict[str, list[Path]]   # только группы len > 1
```

- Хеш считается **потоково** (не читать файл целиком в память — на 4K-видео
  это OOM).
- Решение о дубликате принимается в оркестраторе по множеству уже встреченных
  хешей `seen_hashes`. Первый файл с данным хешем остаётся в нормальной
  структуре, все последующие едут в `Дубликаты/`.
- **Дубликаты переименовываются по дате съёмки так же, как обычные файлы**
  (если дата известна), иначе сохраняют исходное имя. При совпадении имён
  срабатывает `resolve_collision` → `_1`, `_2`.
- Ошибка чтения файла не должна прерывать прогон: файл обрабатывается как
  обычный, в `warnings` пишется причина.

### 5.4. «Мусор» (`mover.is_junk_file`)

```python
is_junk_file(path, photo_max_bytes, video_max_seconds, video_max_bytes) -> str | None
```

- Фото: `размер <= photo_max_bytes` → мусор.
- Видео: `длительность <= video_max_seconds` **или** `размер <= video_max_bytes`
  (что сработает первым).
- `None` в параметре означает «ограничение не задано».
- Возвращается **человекочитаемая причина** (строка) или `None`; все причины
  склеиваются через `"; "` и попадают в отчёт.
- Значение `0` из CLI означает «не задано» и превращается в `None`.
- «Мусор» проверяется **до** определения даты — не тратим время на EXIF
  заведомо ненужных файлов.
- Если `ffprobe` недоступен и длительность получить нельзя — файл **не**
  считается мусором по длительности (лучше оставить, чем ошибочно убрать).

### 5.5. Схема папок назначения (`mover.build_destination_path`)

```
<dest_root>/
└── <Год>_media/
    └── <ММ>.<ГГГГ>_media/
        ├── <ММ>.<ГГГГ>_photo/   # обычные изображения
        ├── <ММ>.<ГГГГ>_video/   # видео
        └── <ММ>.<ГГГГ>_raw/     # RAW-файлы (отдельно!)
```

Специальные папки (в корне `dest_root`):
`Дата_не_определена/`, `Дубликаты/`, `Мусор/`.

Функция:

```python
build_destination_path(
    dest_root: Path,
    filename: str,
    date: datetime | None = None,
    special_folder: str | None = None,
    rename_by_date: bool = False,
) -> Path
```

Порядок проверок: переименование → `special_folder` → `date is None` →
`RAW` → `IMAGE` → `VIDEO` → прочее.
**Проверка RAW обязана стоять перед IMAGE**, иначе RAW уедет в `_photo`.

### 5.6. Переименование

```python
build_renamed_filename(filename, date) -> str
# 'IMG_20200325_114014.jpg' -> '2020-03-25_11-40-14.jpg'
```

Формат: `%Y-%m-%d_%H-%M-%S` + исходное расширение (регистр расширения
сохраняется). Если даты нет — вернуть имя как есть.

### 5.7. Безопасное перемещение (`mover`)

```python
resolve_collision(dest_path) -> Path
# при существовании файла: name_1.ext, name_2.ext, ...

move_file_safely(src, dest, dry_run=False) -> tuple[Path, str]
# статусы: 'planned' | 'moved' | 'error'
```

Требования:
- `dest.parent.mkdir(parents=True, exist_ok=True)` перед перемещением.
- Никогда не перезаписывать существующий файл.
- `shutil.move` в `try/except (OSError, shutil.Error)` → статус `'error'`,
  файл остаётся на месте, ошибка логируется и попадает в `errors.log`.
- В `dry_run` возвращается итоговый путь со статусом `'planned'`, диск не
  трогается вообще.

### 5.8. Обход источника и многопоточность

```python
collect_media_files(root, extensions, exclude=None) -> list[Path]
```

- Рекурсивный обход; отбрасывание не-файлов и неподдерживаемых расширений.
- **Исключить папку назначения**, если она вложена в источник (иначе при
  повторном прогоне программа начнёт сортировать собственный результат —
  проверка через `_is_relative_to`).
- Пропускать служебные папки: `Дубликаты`, `Мусор`, `Дата_не_определена`.
- При числе файлов больше порога (`THREADING_THRESHOLD = 10_000`) включать
  `ThreadPoolExecutor`; иначе обрабатывать последовательно (на малых объёмах
  потоки только замедляют из-за I/O-конкуренции).
- Общий доступ к `seen_hashes` и `gps_index` защищать `threading.Lock`.
- Прогресс выводить только при `sys.stdout.isatty()` (иначе ломается лог
  в GUI / перенаправленном выводе).

### 5.9. Результат обработки одного файла

```python
@dataclass
class ProcessResult:
    record: dict          # строка для CSV
    category: str         # 'ok' | 'duplicate' | 'junk' | 'error'
    date: datetime | None
    messenger: str | None
```

Запись отчёта: `source_path, dest_path, date_source, date_value,
is_approximate, warnings, hash`.

Порядок шагов в `process_single_file` (строго):

1. определить мессенджер по имени (только для статистики);
2. проверить «мусорность» → в `Мусор/`;
3. определить дату (EXIF → видео → имя → mtime);
4. если даты нет — попытаться восстановить по GPS;
5. обновить GPS-индекс;
6. построить путь + переименовать по дате;
7. проверить дубликат по MD5 → в `Дубликаты/`;
8. переместить;
9. вернуть запись.

## 6. Подсистема 2: реорганизация архива

Назначение — работать с **уже существующим** деревом папок, имена которых
исторически произвольны.

### 6.1. Автоопределение уровня (`detector.detect_level`)

Скрипт запускается с `--root` и сам понимает, что ему дали:

| Уровень | Признак | Что делает |
|---|---|---|
| `archive_root` | большинство подпапок — годовые (`2024`, `2024_Фото`) | обрабатывает годы → месяцы |
| `year` | большинство подпапок — месячные (`05.2024`, `Май 2024`) | обрабатывает месяцы |
| `month` | подпапок нет, есть файлы | переносит в структуру года/месяца |
| `unknown` | ничего не подошло | отказывается работать с внятным сообщением |

Уровень определяется **по большинству прямых потомков**, а не по первому
встречному. Смешанные папки не должны приводить к неверному решению.

### 6.2. Разбор имён папок (`date_parser`)

Поддерживаемые форматы **года**: `2024`, `2024_Яманькины`, `Photos_2024`,
`2024_yamankin_media`.

**Диапазоны** (`2003-2005`, `2003–2005`) распознаются и **исключаются** из
обработки — это не годовая папка.

Форматы **месяц-год**: `05.2024`, `2024-05`, `05-2024`, `Май 2024`, `May_2024`,
`10.2017 Ч`.

Словари месяцев: русские (полные, родительный падеж, сокращения) и английские
(полные + 3-буквенные). Регистронезависимо.

**EXIF-фолбэк:** если из имени папки месяц определить нельзя — взять год и
месяц из `DateTimeOriginal` самого старого файла в папке.

### 6.3. Именование папок (`renamer`)

```python
year_folder_name(year)        -> '2024_media'
month_folder_name(m, y)       -> '05.2024_media'
image_folder_name(m, y)       -> '05.2024_photo'
video_folder_name(m, y)       -> '05.2024_video'
```

Неизвестная дата → `_unknown_media`.

### 6.4. Обработка

- Переименование папки выполняется **безопасно**: если целевая уже существует —
  `resolve_collision` (суффикс), никогда не слияние «наугад».
- Внутри месячной папки создаются `*_photo` и `*_video`, файлы перемещаются по
  типу. **Прочие файлы остаются на месте** и фиксируются в отчёте (их не
  трогаем — там могут быть `.txt`, `.psd`, проектные файлы).
- Пустые папки не удаляются автоматически.

### 6.5. Порядок работы CLI

1. валидация `--root`;
2. определение уровня;
3. подсчёт плана (сколько годов / месяцев / фото / видео / прочих) —
   **до** любых изменений;
4. вывод плана пользователю;
5. запрос подтверждения (если не `--dry-run` и не `--yes`);
6. выполнение;
7. отчёты: `report.csv`, `errors.log`, `summary.txt` + сводка в stdout.

## 7. CLI-контракт (подсистема 1)

```
python sort_media.py --source PATH --destination PATH [опции]
```

| Флаг | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `--source`, `-s` | путь | **обязателен** | папка-свалка |
| `--destination`, `-d` | путь | **обязателен** | корень результата |
| `--dry-run` | флаг | выкл | только план, без перемещений |
| `--check-duplicates` | флаг | выкл | искать дубликаты по MD5 |
| `--no-junk` | флаг | выкл | не выделять мелкие файлы |
| `--junk-folder` | str | `Мусор` | имя папки для мусора |
| `--photo-junk-max-kb` | float | `2048` | порог фото, `0` = не задан |
| `--video-junk-max-sec` | float | `10` | порог длительности видео |
| `--video-junk-max-kb` | float | `0` | порог размера видео |
| `--extensions` | str | все поддерживаемые | список через запятую |
| `--workers` | int | `1` | число потоков |
| `--yes` | флаг | выкл | без интерактивного подтверждения |
| `--log-file` | путь | `sort_media.log` | лог |
| `--report-file` | путь | `report.csv` | CSV-отчёт |
| `--duplicates-log` | путь | `duplicates.log` | лог дубликатов |
| `--errors-log` | путь | `errors.log` | лог ошибок |

Валидация путей (`validate_paths`): источник существует и это директория;
назначение не является файлом; источник и назначение не совпадают.

Итоговая статистика в stdout: обработано / перемещено / дубликатов / мусора /
без даты / ошибок / время выполнения.

Код возврата: `0` — успех, `1` — ошибка валидации или фатальная ошибка.

## 8. GUI-лаунчер (`launcher.py`)

Отдельное окно **tkinter**, которое не заменяет CLI, а вызывает его как
подпроцесс.

**Элементы:**
- поле «Папка с медиафайлами» + кнопка «Обзор...»;
- поле «Папка назначения» + кнопка «Обзор...»;
- чекбоксы: «Пробный прогон», «Проверять дубликаты», «Папка Мусор»,
  «Переименовывать по дате»;
- поля порогов мусора: фото КБ, видео сек, видео КБ;
- кнопки «Старт», «Открыть отчёт», «Открыть папку результата»;
- область лога с построчным выводом stdout/stderr процесса в реальном времени;
- прогресс/статус.

**Требования:**
- Результаты складывать в подпапку `MS_helper` внутри выбранной папки
  назначения — чтобы результат сортировки не смешивался с оригиналом.
- Запуск через `subprocess.Popen`, чтение вывода в отдельном потоке, опрос
  через `after()` — **GUI не должен зависать**.
- Кнопки блокируются на время работы; по завершении — разблокируются.
- **Никогда не использовать `pythonw.exe`** для запуска консольного скрипта —
  иначе не будет stdout. Если лаунчер сам запущен через `pythonw`, подменять
  путь на `python.exe`.
- Ошибки валидации — через `messagebox.showerror`, а не молча.
- Окно масштабируется под разрешение экрана (базовый размер × коэффициент,
  ограниченный разумными пределами), поддерживается полноэкранный режим.
- Закрытие окна при работающем процессе — спросить подтверждение.

`launcher.vbs` — обёртка для запуска лаунчера двойным кликом без окна консоли.

## 9. Конфигурация и portable-режим

Файл `config.json` рядом со скриптами (или в родительской папке `src/`):

```json
{
  "python_path": "",
  "script_path": "",
  "default_destination": "",
  "last_source": "",
  "default_flags": {
    "check_duplicates": true,
    "junk_folder": true,
    "dry_run_default": false,
    "rename_by_date": true
  },
  "keep_console_open": true
}
```

- При первом запуске конфиг создаётся автоматически с автодетектом путей.
- При повреждённом/битом JSON — не падать, использовать значения по умолчанию.
- Последние выбранные папки запоминаются между запусками.
- Служебные каталоги (`logs/`, `reports/`) создаются при необходимости,
  в portable-режиме — рядом с приложением, иначе в корне.

## 10. Отчёты и логирование

- `report.csv` — **UTF-8 с BOM** (`utf-8-sig`), чтобы Excel открывал кириллицу
  без «кракозябр». Разделитель `;` (русская локаль Excel).
- Колонки: `source_path; dest_path; date_source; date_value; is_approximate;
  warnings; hash`.
- `errors.log` — только ошибки, с путём и текстом исключения.
- `duplicates.log` — список дубликатов и их «первоисточников».
- `sort_media.log` — общий ход выполнения, уровни `INFO`/`WARNING`/`ERROR`.
- Логирование настраивается одной функцией `setup_logging(...)`, пишет и в
  файл, и в stdout (для GUI).
- В строках лога использовать префиксы `ПЛАНИРУЕТСЯ` (dry-run) /
  `ПЕРЕМЕЩЁН` (реально) — пользователь должен видеть разницу.

## 11. Тесты

Набор на `pytest`, каждый модуль покрыт отдельно + интеграционные.

Обязательный минимум:

- `test_date_extractor` — все шаблоны имён, все наборы расширений,
  отсутствие пересечений IMAGE/VIDEO, невалидные даты;
- `test_hash_utils` — одинаковые файлы дают одинаковый хеш, разные — разный,
  индекс и поиск дубликатов, пустой список;
- `test_mover` — все ветки `build_destination_path` (в т.ч.
  **RAW → `_raw`, а не `_photo`**), `resolve_collision`, `move_file_safely`
  в режимах `planned`/`moved`/`error`, `is_junk_file` для фото и видео;
- `test_date_parser` / `test_detector` — все форматы папок, диапазоны годов,
  определение уровня;
- `test_renamer` / `test_file_classifier` — имена папок, классификация;
- `test_integration` — полный прогон на временном дереве: проверить итоговую
  структуру, отчёт, отсутствие потери файлов;
- `test_pipe_hang` — процесс не вешает родителя при большом объёме вывода
  в stdout (защита от дедлока пайпа).

Все тесты работают во временных каталогах (`tmp_path`), не трогают реальные
данные.

## 12. Требования к надёжности

- **Идемпотентность**: повторный запуск на том же источнике не портит
  результат (уже отсортированное не пересортировывается благодаря исключению
  папки назначения).
- **Никаких перезаписей**: только `resolve_collision`.
- **Никаких удалений**: приложение не вызывает `unlink`/`rmtree`.
- **Устойчивость к единичным сбоям**: ошибка на одном файле (нет прав, файл
  занят, битый EXIF, отсутствует `ffprobe`) не останавливает прогон.
- **Кодировка**: все файлы и логи — `utf-8`; при чтении stdout подпроцесса
  явно указывать `encoding='utf-8', errors='replace'`.
- **Windows-специфика**: длинные пути, кириллица в путях, пробелы в путях
  (всегда передавать пути как отдельные элементы списка `cmd`, без `shell=True`).

## 13. Критерии приёмки

1. `python sort_media.py -s <тестовая свалка> -d <out> --dry-run` — печатает
   план, на диске ничего не меняется.
2. Реальный прогон создаёт:
   `out/2024_media/05.2024_media/05.2024_photo|_video|_raw/`.
3. Файл `IMG_20240513_142035.jpg` → `2024_media/05.2024_media/05.2024_photo/2024-05-13_14-20-35.jpg`.
4. Файл `DSC_0001.NEF` с EXIF → `..._raw/` с именем по дате.
5. Два одинаковых файла: первый в структуре, второй в `Дубликаты/` с именем
   по дате.
6. Файл без EXIF и с именем `photo.jpg`, но с валидным `mtime` → попадает в
   структуру по `mtime`, в отчёте `date_source=mtime`, `is_approximate=True`.
7. Повторный запуск не создаёт дублей и не перезаписывает существующие.
8. `reorganize_media.py --root <архив>` корректно определяет уровень и
   печатает план до изменений.
9. `report.csv` открывается в Excel без проблем с кириллицей.
10. `pytest` — зелёный.

## 14. Что НЕ делать

- Не удалять и не перезаписывать файлы.
- Не использовать `shell=True` и не склеивать команды в строку.
- Не тащить тяжёлые зависимости (pandas, PyQt, numpy) — задача решается
  стандартной библиотекой + Pillow/ExifRead.
- Не делать «умное» определение похожих фото (perceptual hash) — только точное
  совпадение MD5. Это осознанное упрощение.
- Не пытаться определять дату по содержимому изображения.
- Не блокировать GUI синхронными вызовами.
- Не молча проглатывать исключения — минимум `logger.debug` в `except`.
